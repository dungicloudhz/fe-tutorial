Bản đồ TypeScript — JavaScript cộng thêm hệ thống kiểu

TypeScript không phải ngôn ngữ mới, mà là một lớp kiểm tra kiểu (type-check) nằm trên JavaScript

TypeScript là gì, giải quyết vấn đề gì?

TypeScript là một ngôn ngữ do Microsoft phát triển, là tập hợp mở rộng (superset) của JavaScript — nghĩa là mọi file JavaScript hợp lệ đều là TypeScript hợp lệ. Điểm khác biệt cốt lõi: TypeScript thêm vào hệ thống kiểu tĩnh (static typing), cho phép khai báo rõ một biến/hàm nhận và trả về kiểu dữ liệu gì. Trình biên dịch tsc sẽ kiểm tra lỗi kiểu ngay khi viết code, trước khi chạy — thay vì JavaScript chỉ phát hiện lỗi lúc runtime. Sau khi biên dịch, TypeScript được chuyển hoàn toàn thành JavaScript thuần để chạy trên trình duyệt hoặc Node.js.

Cài đặt & cấu hình tsconfig.json

Chuẩn bị môi trường trước khi viết dòng TypeScript đầu tiên

Cài đặt & biên dịch
1

Cài TypeScript qua npm

Chạy npm install -D typescript để cài vào dự án, hoặc npm install -g typescript để dùng lệnh tsc toàn cục.

2

Khởi tạo tsconfig.json

Chạy npx tsc --init để sinh file cấu hình mặc định, nơi khai báo cách trình biên dịch xử lý project.

3

Biên dịch sang JavaScript

Chạy npx tsc để biên dịch toàn bộ project, hoặc npx tsc --watch để tự biên dịch lại mỗi khi lưu file.

tsconfig.jsonCONFIG
{
  "compilerOptions": {
    "target": "ES2020",          // phiên bản JS đầu ra
    "module": "ESNext",          // hệ thống module dùng để biên dịch
    "strict": true,               // bật TẤT CẢ kiểm tra kiểu nghiêm ngặt — nên luôn bật
    "outDir": "./dist",          // thư mục chứa file .js sau biên dịch
    "rootDir": "./src",          // thư mục chứa file .ts nguồn
    "esModuleInterop": true,      // cho phép import kiểu CommonJS mượt hơn
    "skipLibCheck": true,         // bỏ qua kiểm tra kiểu trong node_modules cho nhanh
    "forceConsistentCasingInFileNames": true
  },
  "include": ["src/**/*"]
}
✅
Luôn bật "strict": true: Đây là tùy chọn quan trọng nhất — bật hàng loạt kiểm tra như strictNullChecks, noImplicitAny... giúp TypeScript bắt lỗi tối đa. Tắt strict khiến TypeScript gần như chỉ còn tác dụng autocomplete.

Kiểu dữ liệu cơ bản

Primitives, mảng, tuple và các kiểu đặc biệt any / unknown / never / void

Kiểu nguyên thủy (primitives)
primitives.tsTYPES
let ten: string = "An";
let tuoi: number = 25;
let daKichHoat: boolean = true;
let khongCoGiaTri: null = null;
let chuaXacDinh: undefined = undefined;

// TypeScript tự suy luận kiểu (type inference) nếu không khai báo
let diem = 9.5; // tự hiểu là number, không cần viết ": number"
Mảng (array) & Tuple
array-tuple.tsARRAY
// mảng: 2 cách viết tương đương
let diemSo: number[] = [8, 9, 10];
let danhSachTen: Array<string> = ["An", "Bình"];

// tuple: mảng có SỐ LƯỢNG và KIỂU từng vị trí cố định
let nguoiDung: [string, number] = ["An", 25]; // [tên, tuổi]
// nguoiDung = [25, "An"];  ❌ lỗi: sai thứ tự kiểu

// tuple có tên thành phần (dễ đọc hơn), hỗ trợ từ TS 4.0+
let toaDo: [x: number, y: number] = [10, 20];
💡
Khi nào dùng tuple? Dùng khi số phần tử và kiểu từng vị trí đã biết trước, ví dụ trả về cặp [value, setValue] giống useState trong React.
any, unknown, never & void — các kiểu đặc biệt
KiểuÝ nghĩa
anyTắt hoàn toàn kiểm tra kiểu cho biến này — tránh dùng, vì mất hết lợi ích của TypeScript
unknownGiống any nhưng an toàn hơn: phải kiểm tra/ép kiểu trước khi dùng — nên dùng thay any khi chưa biết kiểu dữ liệu
neverKiểu của giá trị không bao giờ xảy ra — hàm luôn ném lỗi, hoặc vòng lặp vô hạn
voidKiểu trả về của hàm không trả về giá trị gì (không có return, hoặc return; trống)
special-types.tsSPECIAL
function ghiLog(msg: string): void {
  console.log(msg); // không return gì cả
}

function baoLoi(msg: string): never {
  throw new Error(msg); // hàm không bao giờ trả về bình thường
}

let duLieu: unknown = JSON.parse('{"ten":"An"}');
// duLieu.ten;  ❌ lỗi: chưa biết duLieu có thuộc tính ten không
if (typeof duLieu === "object" && duLieu !== null && "ten" in duLieu) {
  console.log((duLieu as { ten: string }).ten); // ✅ đã kiểm tra mới dùng
}
⚠️
Tránh any bằng mọi giá: Dùng any tương đương tắt TypeScript cho biến đó — lỗi vẫn xảy ra, chỉ là bạn không được cảnh báo trước nữa. Ưu tiên unknown nếu thật sự chưa biết kiểu.

Type Alias & Interface

Hai cách đặt tên cho một "hình dạng" dữ liệu, dùng nhiều nhất trong TypeScript

Interface — định nghĩa hình dạng object
interface.tsINTERFACE
interface User {
  id: number;
  ten: string;
  email?: string;        // dấu ? = thuộc tính tùy chọn
  readonly taoLuc: Date; // readonly = chỉ gán được lúc khởi tạo
}

const user1: User = {
  id: 1,
  ten: "An",
  taoLuc: new Date()
};
// user1.taoLuc = new Date();  ❌ lỗi: readonly không được gán lại

// interface có thể "extends" (kế thừa) interface khác
interface Admin extends User {
  quyenHan: string[];
}
Type Alias — đặt tên cho bất kỳ kiểu nào
type-alias.tsTYPE
type Point = { x: number; y: number };

// type có thể đặt tên cho union, tuple, primitive... interface thì không
type ID = string | number;
type TrangThai = "cho" | "dangXuLy" | "hoanThanh";

// kết hợp nhiều type bằng "&" (intersection)
type Nguoi = { ten: string };
type NhanVien = Nguoi & { luong: number };

const nv: NhanVien = { ten: "Bình", luong: 15000000 };
Tiêu chíinterfacetype
Đặt tên cho object✅ mạnh nhất✅ được
Đặt tên cho union / tuple / primitive❌ không hỗ trợ✅ được
Mở rộng nhiều lần cùng tên (declaration merging)✅ tự động gộp❌ báo lỗi trùng tên
Kế thừaextends& (intersection)
📌
Quy ước phổ biến: Dùng interface để định nghĩa hình dạng object/class (props, model dữ liệu). Dùng type cho union, tuple, hoặc khi cần kết hợp nhiều kiểu lại với nhau.

Function Types

Khai báo kiểu tham số, giá trị trả về, tham số tùy chọn/mặc định và overload

Kiểu tham số & giá trị trả về
functions.tsFUNCTION
function cong(a: number, b: number): number {
  return a + b;
}

// tham số tùy chọn: dấu ? — phải đứng SAU tham số bắt buộc
function chaoHoi(ten: string, loiChao?: string): string {
  return `${loiChao ?? "Xin chào"}, ${ten}!`;
}

// tham số mặc định: TS tự suy luận kiểu từ giá trị mặc định
function taoUser(ten: string, tuoi = 18) {
  return { ten, tuoi };
}

// rest parameter: gom nhiều tham số thành 1 mảng
function tongTatCa(...soList: number[]): number {
  return soList.reduce((tong, n) => tong + n, 0);
}

// arrow function với kiểu tường minh
const nhan: (a: number, b: number) => number = (a, b) => a * b;
Function Overload — nhiều "chữ ký" cho cùng 1 hàm
overload.tsOVERLOAD
// khai báo các "chữ ký" hàm có thể có (không có phần thân)
function taoThe(id: number): string;
function taoThe(id: number, ten: string): string;

// phần thân thực thi — phải xử lý được mọi trường hợp overload ở trên
function taoThe(id: number, ten?: string): string {
  return ten ? `#${id} - ${ten}` : `#${id}`;
}

taoThe(1);           // ✅ hợp lệ
taoThe(1, "An");     // ✅ hợp lệ
💡
Khi nào cần overload? Khi một hàm có thể được gọi theo nhiều "bộ tham số" khác nhau và kiểu trả về phụ thuộc vào cách gọi — với hàm đơn giản, dùng tham số tùy chọn (?) thường đủ và dễ đọc hơn.

Union, Intersection & Literal Types

Kết hợp nhiều kiểu lại với nhau, hoặc giới hạn giá trị cụ thể

Union Type — "kiểu này HOẶC kiểu kia"
union.tsUNION
function inID(id: string | number) {
  // phải kiểm tra kiểu trước khi dùng phương thức riêng của từng kiểu
  if (typeof id === "string") {
    console.log(id.toUpperCase()); // chỉ string mới có toUpperCase
  } else {
    console.log(id.toFixed(0));    // chỉ number mới có toFixed
  }
}
Literal Type — giới hạn giá trị cụ thể
literal.tsLITERAL
// literal type: biến chỉ được nhận đúng những giá trị liệt kê
type KichThuoc = "nho" | "vua" | "lon";

function datAo(size: KichThuoc) { /* ... */ }

datAo("vua");  // ✅ hợp lệ
// datAo("XL");  ❌ lỗi: "XL" không nằm trong KichThuoc

// kết hợp với union để tạo enum "nhẹ" không cần từ khóa enum
type HuongDiChuyen = "len" | "xuong" | "trai" | "phai";
✅
Literal union rất phổ biến: Thay vì dùng chuỗi tự do dễ gõ sai ("vue" thay vì "vua"), literal type buộc chỉ được chọn 1 trong các giá trị hợp lệ — editor còn tự gợi ý sẵn danh sách.

Enum & const assertions

Đặt tên cho một tập hợp giá trị hằng số cố định

Enum — tập hợp hằng số có tên
enum.tsENUM
enum VaiTro {
  Khach,      // = 0, tự tăng dần nếu không gán giá trị
  NguoiDung, // = 1
  QuanTri    // = 2
}

function kiemTraQuyen(vaiTro: VaiTro) {
  if (vaiTro === VaiTro.QuanTri) console.log("Có toàn quyền");
}

// string enum: rõ ràng hơn khi debug/log ra console
enum TrangThaiDonHang {
  Cho = "CHO_XU_LY",
  DangGiao = "DANG_GIAO",
  HoanThanh = "HOAN_THANH"
}
⚠️
Enum vs Literal union: Nhiều đội nhóm hiện đại (kể cả team TypeScript) khuyên dùng literal union type ("CHO_XU_LY" | "DANG_GIAO") thay vì enum vì nhẹ hơn, không sinh code JS thừa và dễ kết hợp với union khác.
const assertion — "khóa cứng" kiểu về literal
const-assertion.tsAS CONST
let mau1 = "do";             // kiểu suy luận: string (rộng)
let mau2 = "do" as const; // kiểu suy luận: "do" (literal, hẹp)

// dùng "as const" trên object/mảng: mọi thuộc tính thành readonly + literal
const cauHinh = {
  theme: "dark",
  phienBan: 1
} as const;
// cauHinh.theme = "light";  ❌ lỗi: readonly sau khi as const

// rất hữu ích để tạo literal union từ 1 mảng có sẵn
const MAU_SAC = ["do", "xanh", "vang"] as const;
type MauSac = typeof MAU_SAC[number]; // "do" | "xanh" | "vang"

OOP & GENERICS

Classes trong TypeScript

Access modifiers, readonly, abstract class và implements interface

Access modifiers — public, private, protected
class.tsCLASS
class TaiKhoan {
  public ten: string;            // truy cập được từ mọi nơi (mặc định)
  private matKhau: string;      // chỉ truy cập được TRONG class này
  protected soDu: number;      // truy cập được trong class này VÀ class con
  readonly taoLuc = new Date(); // chỉ gán được 1 lần trong constructor

  // cú pháp rút gọn: khai báo + gán tham số ngay trong constructor
  constructor(ten: string, matKhau: string) {
    this.ten = ten;
    this.matKhau = matKhau;
    this.soDu = 0;
  }

  napTien(soTien: number): void {
    this.soDu += soTien;
  }
}

const tk = new TaiKhoan("An", "123456");
tk.napTien(100000);
// tk.matKhau;  ❌ lỗi: private, không truy cập được từ bên ngoài
implements interface & abstract class
abstract.tsABSTRACT
interface CoTheBay {
  bay(): void;
}

// abstract class: không thể "new" trực tiếp, chỉ dùng để kế thừa
abstract class DongVat implements CoTheBay {
  constructor(protected ten: string) {}

  abstract bay(): void; // bắt buộc class con phải tự cài đặt

  gioiThieu(): void { // method dùng chung, class con thừa hưởng luôn
    console.log(`Tôi là ${this.ten}`);
  }
}

class ChimSe extends DongVat {
  bay(): void { console.log(`${this.ten} vỗ cánh bay`); }
}
// new DongVat("x");  ❌ lỗi: không thể khởi tạo abstract class
📌
interface vs abstract class: interface chỉ mô tả "hình dạng" (không có code thực thi). abstract class vừa ép buộc method con phải cài đặt, vừa cho phép chia sẻ code dùng chung giữa các lớp con.
OOP & GENERICS

Generics cơ bản

Viết hàm/class dùng lại được với nhiều kiểu dữ liệu khác nhau, vẫn giữ an toàn kiểu

Vì sao cần Generics?

Nếu viết hàm nhận any, TypeScript sẽ mất khả năng kiểm tra kiểu trả về. Generics cho phép "để trống" một kiểu (thường viết là T) khi định nghĩa hàm/class, rồi kiểu đó sẽ được xác định thực sự khi hàm được gọi — vừa dùng lại được cho nhiều kiểu, vừa giữ nguyên mối liên hệ giữa kiểu đầu vào và đầu ra.

generics-basic.tsGENERIC
// không dùng generic: mất thông tin kiểu, trả về "any"
function phanTuDauXau(arr: any[]): any {
  return arr[0];
}

// dùng generic <T>: đầu vào kiểu gì, đầu ra giữ nguyên kiểu đó
function phanTuDau<T>(arr: T[]): T {
  return arr[0];
}

const so = phanTuDau<number>([1, 2, 3]);   // so có kiểu number
const chu = phanTuDau(["a", "b"]);        // TS tự suy luận T = string, không cần khai báo

// generic class: hộp chứa 1 giá trị kiểu bất kỳ
class Hop<T> {
  constructor(private giaTri: T) {}
  layGiaTri(): T { return this.giaTri; }
}

const hopSo = new Hop<number>(42);
💡
Cách đọc <T>: Hãy nghĩ T như một tham số — giống tham số thường của hàm, nhưng thay vì truyền giá trị, bạn "truyền" một kiểu dữ liệu. Tên T chỉ là quy ước (Type), có thể đặt tên khác như TItem.
OOP & GENERICS

Generic Constraints nâng cao

Giới hạn generic chỉ nhận những kiểu có "hình dạng" nhất định

extends — ràng buộc generic
generic-constraint.tsCONSTRAINT
interface CoDoDai {
  length: number;
}

// T phải là kiểu CÓ thuộc tính "length" — string, array, object có length đều hợp lệ
function inDoDai<T extends CoDoDai>(item: T): T {
  console.log(item.length);
  return item;
}

inDoDai("xin chao");      // ✅ string có length
inDoDai([1, 2, 3]);      // ✅ array có length
// inDoDai(42);           ❌ lỗi: number không có length

// "keyof T": lấy union tất cả tên thuộc tính của T
function layGiaTri<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { ten: "An", tuoi: 25 };
layGiaTri(user, "ten");   // ✅ trả về string
// layGiaTri(user, "diaChi");  ❌ lỗi: "diaChi" không phải key của user
✅
Cặp đôi kinh điển: <T, K extends keyof T> là mẫu cực kỳ phổ biến để viết hàm truy cập thuộc tính an toàn — TypeScript sẽ tự chặn ngay lúc gõ code nếu key không tồn tại trên T.
🟡

Type Narrowing & Type Guards

Thu hẹp kiểu union về kiểu cụ thể trong từng nhánh code

Các cách thu hẹp kiểu phổ biến
narrowing.tsNARROWING
// 1) typeof — cho kiểu nguyên thủy
function xuLy(gtri: string | number) {
  if (typeof gtri === "string") gtri.trim(); // gtri: string
}

// 2) instanceof — cho class
function xuLyLoi(err: Error | string) {
  if (err instanceof Error) console.log(err.message); // err: Error
}

// 3) in — kiểm tra thuộc tính có tồn tại trên object
type Meo = { keu: () => void };
type Cho = { sua: () => void };
function amThanh(vat: Meo | Cho) {
  if ("keu" in vat) vat.keu(); // vat: Meo
  else vat.sua();          // vat: Cho
}

// 4) custom type guard — hàm trả về "gtri is KieuX"
function laChuoi(gtri: unknown): gtri is string {
  return typeof gtri === "string";
}
function inHoa(gtri: unknown) {
  if (laChuoi(gtri)) console.log(gtri.toUpperCase()); // gtri: string
}
💡
Custom type guard hữu ích khi nào? Khi kiểm tra kiểu phức tạp hơn typeof/instanceof cho phép, ví dụ kiểm tra một object có đủ các thuộc tính của interface hay không — gói logic đó vào 1 hàm dùng lại nhiều nơi.
KIỂU NÂNG CAO

Discriminated Unions

Mẫu thiết kế cực mạnh: dùng 1 thuộc tính chung để TypeScript tự phân biệt từng nhánh union

Thuộc tính "kind" làm điểm phân biệt
discriminated-union.tsDISCRIMINATED
interface HinhTron {
  kind: "tron";    // "kind" là thuộc tính phân biệt (discriminant)
  banKinh: number;
}
interface HinhVuong {
  kind: "vuong";
  canh: number;
}
type Hinh = HinhTron | HinhVuong;

function tinhDienTich(hinh: Hinh): number {
  switch (hinh.kind) {
    case "tron":
      return Math.PI * hinh.banKinh ** 2; // hinh tự thu hẹp thành HinhTron
    case "vuong":
      return hinh.canh ** 2;          // hinh tự thu hẹp thành HinhVuong
  }
}
✅
Rất phổ biến khi mô hình hóa trạng thái: Ví dụ trạng thái gọi API {kind:"loading"} | {kind:"success", data} | {kind:"error", message} — switch(kind) giúp không bao giờ quên xử lý 1 trạng thái, và TypeScript báo lỗi ngay nếu thiếu case.

Utility Types

Bộ công cụ có sẵn của TypeScript để biến đổi type đã có thành type mới

Các Utility Type dùng nhiều nhất
Utility TypeCông dụng
Partial<T>Biến mọi thuộc tính của T thành tùy chọn (?) — hữu ích khi update 1 phần object
Required<T>Ngược lại Partial — bắt buộc mọi thuộc tính phải có giá trị
Readonly<T>Biến mọi thuộc tính thành chỉ đọc, không gán lại được
Pick<T, K>Chọn ra một tập con thuộc tính K từ T
Omit<T, K>Loại bỏ tập thuộc tính K khỏi T, giữ lại phần còn lại
Record<K, V>Tạo kiểu object với key thuộc K, value đều thuộc kiểu V
ReturnType<F>Lấy ra kiểu giá trị trả về của hàm F
utility-types.tsUTILITY
interface SanPham {
  id: number;
  ten: string;
  gia: number;
  moTa: string;
}

// Partial: dùng khi chỉ update 1 vài trường
function capNhatSanPham(id: number, thayDoi: Partial<SanPham>) { /* ... */ }
capNhatSanPham(1, { gia: 99000 }); // ✅ chỉ cần truyền đúng 1 trường

// Pick: chỉ lấy ra id và ten, dùng cho danh sách rút gọn
type SanPhamRutGon = Pick<SanPham, "id" | "ten">;

// Omit: bỏ id ra vì id sẽ do server tự sinh khi tạo mới
type SanPhamMoi = Omit<SanPham, "id">;

// Record: object dạng "bảng tra cứu" theo key
type GioHang = Record<number, number>; // { [productId: number]: soLuong }
const gio: GioHang = { 1: 2, 5: 1 };

// ReturnType: lấy kiểu trả về mà không cần viết lại
function taoUser() { return { id: 1, ten: "An" }; }
type UserType = ReturnType<typeof taoUser>; // { id: number; ten: string }
💡
Không cần nhớ hết: Chỉ cần thuộc Partial, Pick, Omit, Record — 4 utility type này chiếm phần lớn nhu cầu thực tế hằng ngày khi làm việc với API và form.

Mapped Types & Conditional Types

Tự viết "công thức" biến đổi type — nền tảng đứng sau mọi Utility Type có sẵn

Mapped Type — lặp qua từng thuộc tính của T
mapped-type.tsMAPPED
// đây thực chất là cách Partial được viết bên trong TypeScript
type PartialCuaToi<T> = {
  [K in keyof T]?: T[K];
};

// tự viết mapped type riêng: biến mọi thuộc tính thành kiểu hàm getter
type Getters<T> = {
  [K in keyof T as `get${string & K}`]: () => T[K];
};
type User = { ten: string; tuoi: number };
// UserGetters = { getTen: () => string; getTuoi: () => number }
type UserGetters = Getters<User>;
Conditional Type — "nếu ... thì ..." ở cấp độ kiểu
conditional-type.tsCONDITIONAL
// cú pháp: T extends U ? KieuNeuDung : KieuNeuSai
type LaMang<T> = T extends any[] ? "co" : "khong";
type A = LaMang<string[]>; // "co"
type B = LaMang<number>;   // "khong"

// infer: "trích xuất" 1 kiểu con từ bên trong kiểu phức tạp
type PhanTuCuaMang<T> = T extends (infer U)[] ? U : never;
type C = PhanTuCuaMang<number[]>; // number
📌
Không cần thành thạo ngay: Mapped & Conditional Type là kiến thức nâng cao, chủ yếu dùng khi viết thư viện dùng chung. 90% công việc thực tế chỉ cần dùng thành thạo các utility type có sẵn ở phần trước.

import / export

Async/Await & Promise<T>

Khai báo kiểu cho code bất đồng bộ — gọi API, đọc file, chờ timer

Promise<T> — T là kiểu giá trị "sẽ có" trong tương lai
async-await.tsASYNC
interface User { id: number; ten: string; }

// hàm async luôn trả về Promise, dù bạn chỉ viết "return T"
async function layUser(id: number): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) {
    throw new Error("Không lấy được user");
  }
  const du: User = await res.json();
  return du; // TypeScript tự bọc lại thành Promise
}

// gọi và xử lý lỗi bằng try/catch
async function main() {
  try {
    const user = await layUser(1);
    console.log(user.ten);
  } catch (loi) {
    // biến bắt trong catch mặc định có kiểu "unknown", phải kiểm tra trước khi dùng
    if (loi instanceof Error) console.error(loi.message);
  }
}

// Promise.all: chờ nhiều promise, kiểu trả về là tuple tương ứng
async function layNhieuUser() {
  const [u1, u2] = await Promise.all([layUser(1), layUser(2)]);
}
⚠️
Biến trong catch luôn là unknown: TypeScript không biết code nào ném ra lỗi gì, nên luôn cần instanceof Error hoặc kiểm tra kiểu trước khi đọc thuộc tính như .message.

Props & State trong React (.tsx)
Button.tsxREACT
import { useState } from "react";

// interface mô tả rõ props: tên, kiểu, có bắt buộc hay không
interface ButtonProps {
  nhan: string;
  onClick: () => void;
  disabled?: boolean; // props tùy chọn
}

function Button({ nhan, onClick, disabled = false }: ButtonProps) {
  // useState: khai báo rõ kiểu state, tránh TS suy luận sai
  const [soLanClick, setSoLanClick] = useState<number>(0);

  return (
    <button disabled={disabled} onClick={() => {
      setSoLanClick((n) => n + 1);
      onClick();
    }}>
      {nhan} ({soLanClick})
    </button>
  );
}
✅
Luôn định nghĩa interface Props riêng: Đặt tên rõ ràng (ButtonProps) thay vì inline — dễ tái sử dụng, dễ đọc, và editor gợi ý chính xác khi component được dùng ở nơi khác.
MẸO & LỖI HAY GẶP

Best Practice & lỗi hay gặp

Những sai lầm phổ biến của người mới học TypeScript

✅ NÊN LÀM
Luôn bật strict: true trong tsconfig.json
Không có strict mode, TypeScript bỏ qua rất nhiều lỗi tiềm ẩn quan trọng như giá trị null/undefined không được kiểm tra — gần như phí phạm lý do dùng TypeScript.
✅ NÊN LÀM
Ưu tiên để TypeScript tự suy luận kiểu (type inference)
Chỉ khai báo kiểu tường minh khi TS không tự suy luận được (tham số hàm, kiểu trả về của hàm public) — khai báo thừa ở mọi biến làm code rườm rà không cần thiết.
❌ TRÁNH
Lạm dụng any hoặc ép kiểu as để "cho qua" lỗi
Dùng any/as để tắt lỗi đỏ thường chỉ chuyển lỗi từ lúc biên dịch sang lúc chạy thực tế — hãy sửa đúng kiểu dữ liệu thay vì ép TypeScript im lặng.
❌ TRÁNH
Quên xử lý null/undefined khi strictNullChecks bật
Với strict mode, mọi biến có thể null đều bắt buộc kiểm tra trước khi dùng — đừng dùng dấu ! (non-null assertion) tùy tiện chỉ để code biên dịch được.
Bảng lỗi thường gặp
LỗiNguyên nhân & cách sửa
Object is possibly 'undefined'Truy cập thuộc tính trên giá trị có thể undefined — dùng optional chaining ?. hoặc kiểm tra if trước
Type 'X' is not assignable to type 'Y'Gán sai kiểu dữ liệu — kiểm tra lại kiểu khai báo có đúng với giá trị thực tế không
Property does not exist on typeTruy cập thuộc tính không có trong interface/type — kiểm tra tên gõ đúng chưa, hoặc thêm thuộc tính vào type
Argument of type X is not assignable to parameter of type YTruyền sai kiểu tham số khi gọi hàm — đối chiếu lại kiểu tham số hàm yêu cầu
